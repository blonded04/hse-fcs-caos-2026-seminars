Пример сравнивает создание, заполнение, чтение и утилизацию короткоживущих
объектов в C (`malloc/free`) и Java HotSpot (TLAB + SerialGC).

Нужны Bash, clang/GCC, JDK 21+ и `/usr/bin/time`. Запуск из этого каталога:

```bash
./run.sh
```

По умолчанию каждый процесс обрабатывает 500 000 пачек по 1024 объекта:
512 млн объектов после прогрева. Выполняются три отдельных запуска C и Java,
порядок чередуется. Это несколько секунд работы; точное время зависит от машины.
Можно уменьшить объём или увеличить до 1 000 000 пачек:

```bash
./run.sh 100000 1   # 102,4 млн объектов, один запуск каждой реализации
./run.sh 1000000 3 # 1,024 млрд объектов, три запуска
```

`CC`, `JAVA` и `JAVAC` позволяют выбрать исполняемые файлы компилятора/JDK.
Бинарные файлы создаются во временном каталоге и автоматически удаляются.
Сборка выполняется до вызова `time`.

Программы печатают `elapsed_ms` — миллисекунды основного workload после
прогрева. Внешний `/usr/bin/time -p` дополнительно печатает **секунды**:
`real` — полное время процесса, `user` и `sys` — его CPU time. `real` включает
старт JVM, JIT, прогрев и GC. В конце скрипт сравнивает медианы именно `real`.
Отношение C / Java больше единицы означает, что Java затратила меньше времени.

Пример проверенного запуска с параметрами по умолчанию (macOS 15.7.3 arm64,
HotSpot 21.0.7): медиана `real` **C 6,41 с; Java 1,57 с**, отношение **4,08×**.
В измеряемой части каждого Java-запуска прошли 458 сборок мусора. Это
наблюдение на конкретной машине, не обещание такого же отношения на другой.

В обеих программах объект содержит два 64-битных числа (16 байт payload).
Вся пачка создаётся до чтения её полей. C индивидуально освобождает объекты,
Java удаляет ссылки из переиспользуемого глобального массива. Все checksum
должны совпадать; скрипт проверяет это автоматически.

Глобальный массив Java и `-XX:-DoEscapeAnalysis` исключают scalar replacement;
счётчик `allocated_bytes` подтверждает реальные heap allocations. В этой
конфигурации ожидается примерно 32 байта на Java-объект. `gc_count` показывает
число сборок внутри измеряемого workload. C собирается с
`-fno-builtin-malloc -fno-builtin-free`, чтобы компилятор сохранил обращения
к аллокатору. Межъязыковых вызовов JNI/FFI нет.

Это благоприятная нагрузка для TLAB и young GC: почти все объекты быстро
становятся недостижимыми. Java получает heap 128 MiB и освобождает память
областями. Используется однопоточный SerialGC. Сравнение не предполагает
одинаковый RSS: JVM расходует память на отложенную утилизацию, заголовки и
runtime. Финальная полная GC принудительно не запускается. Производительность
меняется с выживаемостью объектов, размером heap, ОС и реализацией malloc;
скрипт показывает измеренное отношение, а не гарантирует победителя.
Пул/region allocator в C может существенно сократить разрыв.

На macOS скрипт снимает унаследованное переопределение `MallocNanoZone`, чтобы
обычная политика системного malloc не заменялась отключением nano allocator.
На Linux сравнение будет с malloc используемой libc. Источники устройства:
[TLAB в HotSpot](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/gc/shared/threadLocalAllocBuffer.inline.hpp),
[сборщики HotSpot](https://docs.oracle.com/en/java/javase/21/gctuning/available-collectors.html).
